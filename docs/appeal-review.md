# 复核人工作流

判定未通过之后，用户在冻结窗口内提出申诉，进入 `APPEAL`。这份文档定义复核人（人，不是模型）该怎么处理。

## 拿到一条申诉，按顺序看四件事

**第一步：条款是不是写清楚了。**
如果条款本身有歧义（例如"写完整一章"没定义章节长度），处理方式是**撤销原判**。规则不清时不得扣款——这条没有例外，否则所有歧义都会变成对用户不利的解释。

**第二步：证据能不能复算。**
DC-A 条款必须能重算。复核人自己跑一遍计算：

- 字数：自己数一遍。差 30 字以内要特别小心，可能是统计口径不同（是否计入标点、是否计入标题）。
- 时间：以服务端接收时间为准。客户端时间戳一律不作依据。
- 要素：做全文检索，包括同义表述、代称、分段后的变体。

只要复核人算出的结果与原判定不一致，**撤销原判**。不存在"技术上差一点但实质达标"的裁量空间。

**第三步：引用能不能定位。**
DC-B 条款的 `quote` 必须在原文里逐字存在。复核人复制引用去原文搜一遍：

- 搜不到 → 撤销原判（该条款本应降级为"无法判定"）。
- 搜得到但含义被曲解（例如把角色台词当成叙述）→ 撤销原判。
- 搜得到且含义正确 → 进入第四步。

**第四步：模型结论是否越界。**
模型只能判列出的条款。如果模型的理由里出现了"文笔欠佳""不够吸引人""完成度不高"这类条款之外的表述，**该条款的结论无效**，撤销原判。

---

## 四种处理结果

| 情况 | 处理 | 资金 |
|---|---|---|
| 条款有歧义 | 撤销原判 | 全额退回 |
| 证据复算不一致 | 撤销原判 | 全额退回 |
| 引用无法定位或被曲解 | 撤销原判 | 全额退回 |
| 模型评判了条款之外的内容 | 撤销原判 | 全额退回 |
| 证据完整、复算一致、引用准确 | 维持原判 | 按阶梯划转 |

**注意这张表的方向**：四种情况里有四种是撤销，一种是维持。这是刻意的。复核的默认假设应该是"原判定可能错了"，而不是"用户在狡辩"。

---

## 复核记录必须写什么

复核不是点一个"通过/驳回"按钮。必须产出与 `SPEC.md` §5 同构的记录：

```json
{
  "engine": { "kind": "human", "reviewer": "r-1024", "at": "2026-11-06T10:20:00+08:00" },
  "verdict": "overturned | upheld",
  "criterionId": "c3",
  "originalEvidence": "缺少要素：旧信",
  "reviewNote": "原文第 2 段有「那封没寄出的信」，与要素「旧信」指同一物件，要素判定有误",
  "recomputed": "全文检索「信」共 6 处，其中第 2 段指称命中"
}
```

`reviewNote` 是给用户看的那句话。写"不符合规则"是无效的——用户需要知道具体错在哪，否则下一次还是会犯同样的判定错误。

---

## 复核人不得有的三种状态

1. **不得因维持原判获得收益。** 复核人的报酬与划转金额无关，且不得按件计酬（按件计酬会激励快速驳回）。
2. **不得复核自己参与制定的条款。** 任务创建时的审核人与复核人必须分离。
3. **不得在超时压力下批量处理。** 复核有时限（建议 48 小时），但不得设置"每小时处理 N 条"的考核。

---

## 复核的元问题

如果申诉率超过 15%，说明问题不在复核环节，而在判定环节——条款设计太模糊、DC-B 用得太滥、或者模型被赋予了不该有的权限。这时候应该停下来改协议，而不是加人手。

复核能力的上限决定了产品能承载多少用户。以 10% 申诉率、日活 1 万估算，每天 1000 次复核，人力不可承受。所以这份协议 §12 把"人工复核成本"列为**可能导致设计被推翻的假设之一**——在验证之前，不要把产品建在它上面。
